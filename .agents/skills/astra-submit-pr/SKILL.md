# 提交文档修订 PR

在用户要求提交或更新本任务 PR 时执行。遵循仓库根目录 AGENTS.md；读取[标准 PR 模板](references/pr-template.md)，这是 PR 正文的唯一模板，不另维护副本。不需要安装脚本或 CI。

## 明确任务与比较范围

1. 读取当前说明书、项目 Handoff、本任务 Handoff，以及为本次 PR 明确指定的 notes.md / proposal.md。任务不明确时询问任务标识，不扫描其他任务目录。首次结构迁移可由用户明确授权读取旧文档。
2. 检查 `git status --short --branch`、remote、完整差异和已暂存改动。当前为 main 时先建立 `docs/<owner>/<topic>` 工作分支；保留其他人的改动，不擅自归入本任务。
3. fetch origin，记录任务原始起点和最近比较的 main 完整 SHA。首次任务记录起点后不覆盖；检查候选分支与 main 的分歧，不盲目合并其他提交。
4. 已有该分支 PR 时读取并更新；没有则创建。Issue 可选，不强制新建。允许定向读取当前 PR 的评论和起点/最新 main，不加载无关历史。

## 检查并保存

- 阅读最终候选稿和 diff，检查本次编号定义有无重复/重排/复用，原有约束是否被无意删除；新增与废止项需要理由和状态。
- 检查相对文件链接及改动涉及的章节引用、正文与纪要/提案/Handoff 是否一致，运行 `git diff --check`。迁移时加查原条目覆盖及归档完整性。
- 特别检查示例、建议、未决项是否升级为确认；事实、权限、执行状态及恢复能力是否被悄悄改变。说明书应能独立使用，不能依赖旧稿补全。
- 不把未做的检查写为通过，不把 Skill 检查称作 CI 或业务运行验证。发现错误先修正；无法解决的语义问题明确列出，PR 标为 Draft，不能宣称可合并。
- 更新本任务纪要及 Handoff 的进度、检查、阻塞和下一步；只有项目状态变化或准备合并时更新项目 Handoff。
- 仅暂存明确属于本次任务的路径，审查暂存 diff，再以 `docs: 中文摘要` 提交。无新差异则复用已有提交，不造空提交。
- 首次推送用 `git push -u origin <工作分支>`，不能继承 origin/main 作为目标；后续核对 upstream 后 push。fetch 并核对远程 head、文件树和本地工作区。
- 命令行凭证失败则保留本地提交，记录限制，可使用已授权 GitHub 连接器。连接器提交必须基于目标工作分支的当前 head，保持正常前进，不能强推或修改 main；若生成 SHA 与本地不同，先核对文件树、保留本地备份分支，再在干净工作区切换至跟踪远程的分支。不能安全对齐则报告，不 reset 或清理未知文件。

## 创建或更新 PR

使用模板填写全部栏目；空栏目写“无”或“未执行及原因”，不要留下占位符。标题为 `docs: 专题修订摘要`，base 为 main，head 为本任务工作分支。

修订摘要需解释实际结论变化，不只列文件。README、AGENTS、Skill 等协作文件也须列影响；结构迁移属于协作变更，不能写成业务新增需求。

优先使用已连接的 GitHub 工具；无所需能力时使用已授权 CLI。调用前检查 PR 是否已存在，不重复创建。使用结构化正文参数；CLI 使用正文文件，避免多行文本或 shell 替换破坏内容。未获授权的评论、批准、合并和仓库设置变更不属于此流程。

创建成功后将 PR 关联到当前 Codex 聊天；若当前环境没有关联能力则明确说明。返回 PR 链接、实际远程提交 SHA、检查结果及待确认事项。推送失败时报告本地提交和续接命令，不声称 PR 已更新。
